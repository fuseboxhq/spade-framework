# Plan for: Major-work discovery workflow before plan-ready Scopes

**Scope:** PS-2320

**Delivery shape:** One bundle, five tasks, one pull request.

## Technical Approach Summary

Add `/spade-frontier` as a governed pre-Scope workflow that turns a meaningful but foggy destination into a bounded discovery index, one-question-at-a-time resolution records, and one or more human-owned plan-ready Scopes.
Keep the workflow in host-neutral Markdown skill prose, reuse `/spade-research` for isolated fact-finding, permit only disposable evidence-producing prototypes, and use existing Linear, local, and hybrid mode rules without adding a runtime or a sixth SPADE phase.
Define the behavioral oracle before the skill, keep each decision and its evidence at one canonical location, register and project the new skill from `src/`, and release the additive capability as v3.2.0.

## Human Approval Decision Points

### Decision 1: Discovery-map artefact shape by mode

**Recommendation:** Approve a versioned `spade-frontier/v1` index with stable frontier and question identifiers, plus one canonical resolution record per decided question.

- The index records the destination, decisions already made, precisely stated open questions, dependencies, resolution path, AI or human owner, unresolved fog, explicit out-of-scope boundaries, current frontier, blockers, and graduated Scope links.
- In `linear` mode, one dedicated `Frontier: <destination>` work item carries the marked index, and one marker-addressable Linear comment is the canonical resolution record for each decided question.
- In `local` mode, `.spade/frontiers/<slug>/index.md` is the canonical index and `.spade/frontiers/<slug>/decisions/<question-id>.md` is the canonical resolution record.
- In `hybrid` mode, Linear remains canonical and is written first; the local mirror contains the index and canonical pointers but does not copy decision or evidence bodies into a second apparent source of truth.
- The index links to evidence at its native canonical location instead of embedding complete research reports, prototype material, or duplicate decision prose.
- The skill reads the index first and expands only the selected frontier question and its direct dependency or evidence links, keeping large maps bounded.

**Approval requested:** Confirm this index-plus-resolution-record shape, including the intentionally pointer-only hybrid mirror.

### Decision 2: Prerequisite task versus premature delivery

**Recommendation:** Approve a strict evidence-versus-delivery boundary.

- Research may run through `/spade-research` for one question and may become durable only as a concise, human-confirmed resolution record with source links.
- A prototype is allowed only when it is bounded, disposable, isolated from the destination repository and production state, never committed, deployed, imported, or retained as an implementation foundation, and leaves only evidence in the resolution record.
- Any work that creates a durable or reusable artefact, changes repository or external state, handles production data, modifies a schema or configuration, or could ship is delivery rather than discovery.
- Such work becomes or links to a normal SPADE prerequisite Scope, remains outside `/spade-frontier`, and leaves the frontier question blocked until authoritative completion evidence exists.
- A human or organisational prerequisite is recorded with its owner and unblock condition and is never auto-resolved.

**Approval requested:** Confirm that this boundary is strict enough to prevent discovery from becoming unapproved implementation.

### Decision 3: Frontier sessions and v3.1 run-state

**Recommendation:** Keep frontier sessions outside `spade-run-state/v1`.

- Frontier is pre-Scope, while `spade-run-state/v1` requires a stable `scope_id` and permits only the existing Scope, Plan, Approve, Deliver, Evaluate, and complete phase vocabulary.
- The `spade-frontier/v1` map is the lightweight resumable record for discovery and stores only discovery progress, not branch, PR, delivery, or verification state.
- `/spade` may route an unscopable destination to `/spade-frontier`, but it ends the provisional pre-Scope attempt without opening a normal run-state record.
- After graduation, each produced Scope starts an ordinary `/spade` run with its own stable identity and a backlink to the frontier decision index.
- This Scope will not add a `frontier` phase, extend the v1 run-state schema, edit `src/skills/spade/references/continuity.md`, or change `/spade-status` behavior.

**Approval requested:** Confirm the separate map lifecycle and the clean run-state handoff at Scope creation.

### Decision 4: Graduation and human Scope ownership

**Recommendation:** Graduate only when every material question is resolved or explicitly removed from the destination, then route each proposed vertical slice through `/spade-scope` rather than creating Plans directly.

- Each resulting Scope must independently satisfy all required Scope fields, individually verifiable acceptance criteria, architectural constraints, and the existing single-session sizing gate.
- When the destination crosses systems, teams, or independently valuable outcomes, graduation produces an ordered set of Scopes with explicit dependencies instead of one oversized Scope.
- The human confirms each Scope's intent, boundaries, consequential decisions, and final filing before it becomes canonical.
- The frontier index becomes the concise decision index and links to the resulting Scopes; each Scope links back without copying the complete discovery record.
- Graduation is the postcondition of the invocation that resolves the final material question, not a third continuation mode that can perform unbounded work.
- When an external prerequisite becomes complete, validating its authoritative completion evidence is the resolution of that one blocked frontier question.
- Graduation never creates Plan tasks, approves a Plan, writes implementation code, or marks a Scope Done.

**Approval requested:** Confirm this graduation bar and the use of normal `/spade-scope` ownership and persistence.

### Decision 5: File-count tripwire and one-bundle delivery

**Recommendation:** Approve a one-bundle exception to `.spade/config`'s 12-file ceiling.

- The canonical skill, references, fixtures, capability inventory, release metadata, lifecycle transition, documentation, and deterministic host projections will exceed 12 files.
- The five tasks share one map schema, command contract, behavioral corpus, capability version, and direct dependency arrows.
- Splitting them would create an installable command without its full behavior or a release surface that does not match its canonical source.

**Approval requested:** Approve one branch and one PR despite the expected generated-file overage.

## Architectural Alignment and Conflicts

- **No architectural conflict found.**
  The Plan remains Markdown plus bounded shell and standard-library lint, uses existing host primitives, and adds no service, database, daemon, package dependency, or external integration.
- **The new skill is orthogonal rather than casual command sprawl.**
  `/spade-scope` assumes the work can become plan-ready in one session, `/spade-research` answers one ephemeral fact-finding question, and `/spade` begins the normal loop around a Scope.
  `/spade-frontier` owns the missing multi-invocation pre-Scope decision map and subsumes none of those existing contracts.
- **Destination and strategy remain human-owned.**
  `/spade-frontier` requires a meaningful human-authored destination, may structure questions and recommend evidence paths, and must refuse to invent portfolio priorities, business strategy, or the reason the destination matters.
- **Canonical source and projections remain separated.**
  All behavior is edited under `src/`, while Claude, Codex, plugin, marketplace, install-manifest, and top-level skill surfaces are regenerated by `scripts/project-hosts.sh`.
- **`src/skills/spade-review/SKILL.md` remains untouched.**
  The review skill does not own the global command inventory or any frontier transition, so the new command need not be added to a list inside it.
  If delivery proves otherwise, stop and revise the Plan instead of editing the file within its 83-byte headroom.
- **PS-2420 remains isolated.**
  This work will not edit `/spade-status` recommendations, the existing FRAMEWORK continuity wording, or boundary-conditional validation in `continuity.md`.
  The frontier/run-state distinction will live in the new skill contract and a dedicated discovery section rather than modifying those lines.
- **The supplied Scope excerpt omits formal Dependencies, Context, and Origin fields required by the current Scope contract.**
  This Plan assumes PS-2319 and PS-2322 are merged prerequisites, the existing Scope-authoring and research workflows are upstream, normal plan-ready Scopes are downstream, and PS-2320 is the origin.

## Risks and Assumptions

- **R1 - Ceremony without fog:** A discovery command can become an attractive nuisance for work that is already Scope-ready.
  Mitigation: run an in-memory fog gate before any write and route directly to `/spade-scope` when all consequential boundaries and decisions are already clear.
- **R2 - Map growth:** A long initiative can exceed useful context if every answer and evidence body is copied into the index.
  Mitigation: keep the map as a bounded index and load only the selected question plus direct dependencies and canonical evidence pointers.
- **R3 - Duplicate authority:** Linear comments, local files, Scope descriptions, and research reports could each appear to own the same answer.
  Mitigation: require exactly one canonical resolution record per question, store only pointers elsewhere, and make hybrid authority explicit.
- **R4 - Concurrent progression:** Two invocations could resolve the same question or advance from stale dependencies.
  Mitigation: re-read the canonical index immediately before writing, verify the selected question is still on the current frontier, and halt for reload if the index revision, dependencies, or answer pointer changed.
- **R5 - Prototype escape:** Throwaway code may quietly become production code or leave external state behind.
  Mitigation: use an isolated temporary location, prohibit destination-repo and production mutation, retain only the observation, and reclassify any reusable output as a prerequisite Scope.
- **R6 - Human decision laundering:** An AI recommendation could be recorded as a consequential human decision.
  Mitigation: mark ownership on every question, require explicit human confirmation for human-owned answers, and record attribution in the canonical resolution record.
- **R7 - Premature graduation:** A map can look tidy while one unresolved dependency still changes Scope intent, boundaries, feasibility, or acceptance criteria.
  Mitigation: run a graduation readiness check against every question, dependency, unresolved-fog entry, and the `/spade-scope` quality and sizing gates.
- **R8 - Research persistence mismatch:** `/spade-research` is ephemeral by default, while frontier decisions must be durable.
  Mitigation: preserve the research skill's one-question and read-only contracts, then ask the human to confirm the concise answer and cited sources before `/spade-frontier` writes its own canonical resolution record.
- **R9 - Generated-file volume:** Host projections and release fixtures will dominate the diff and cross the autonomy file ceiling.
  Mitigation: keep one semantic bundle, audit canonical files separately from generated outputs, and require the explicit exception in Decision 5.
