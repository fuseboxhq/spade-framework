# Plan for: Continuity: resumable SPADE runs and learning-candidate capture

**Scope:** PS-2322

**Plan status:** Approved on 2026-07-14

**Expected release:** v3.1.0

**Technical Approach Summary:**
Extend the existing run trace with a versioned, mode-neutral current-state summary while preserving its append-only event history.
Keep the contract in host-neutral skill prose and per-project Markdown or tracker artefacts, validate every recorded claim against live tracker, repository, branch, and PR state before offering continuation, and route high-signal delivery or evaluation lessons through the existing human-gated `/spade-learn` flow.
Add a blind behavioral corpus before changing behavior, then regenerate all host projections and release surfaces from `src/` for v3.1.0.

**Architecture Alignment:**

- The Plan conforms to the repository's Markdown-and-shell architecture and introduces no daemon, service, database, package dependency, or separate context-save skill.
- Detailed continuity and candidate rules will use progressively disclosed canonical references, while the always-loaded skills retain routing, invariants, refusal rules, and completion behavior.
- Tracker state remains canonical in `linear` and `hybrid` modes, local state remains canonical in `local` mode, and the hybrid mirror remains explicitly non-authoritative.
- The Plan does not require changes to `src/skills/spade-review/SKILL.md`, which has only 83 bytes of authoring-budget headroom.
- If delivery proves that `src/skills/spade-review/SKILL.md` must change, this Plan is invalid at that point and must be revised so the first operation moves branch-specific content into `references/` before adding any new contract text.
- No architectural conflict with `ARCHITECTURE.md`, `PATTERNS.md`, or `ANTI-PATTERNS.md` was found.

### Prior Learnings Considered

- *Any write into a consumer file must be idempotent via delimited markers, never append* (`2026-04-22-onboarding-must-be-idempotent.md`) - the local run-state summary will use one bounded, replaceable versioned region, refuse malformed or duplicate regions, and retain event history separately instead of blindly appending competing summaries.

**Risks and Assumptions:**

- Linear comments are append-oriented, so the recommended contract appends a complete immutable state snapshot at each checkpoint and selects the newest well-formed snapshot by authoritative tracker ordering while retaining older snapshots as history.
- A trace is evidence about what the orchestrator recorded, not proof that tracker state, a branch, a commit, a worktree, or a PR still exists.
- Scope or Plan revision, stale approval, a missing branch, a changed PR head, malformed state, or an unexplained dirty worktree must prevent automatic continuation.
- Dirty worktree handling must preserve user changes and must never use automatic stash, reset, checkout, deletion, or inferred ownership.
- Candidate detection can become noisy or leak sensitive detail unless it is constrained to explicit delivery and evaluation evidence, deduplicated before display, and routed through the existing public-safe, private, or skip decision.
- Canonical changes plus required generated projections will exceed `.spade/config`'s 12-file autonomy ceiling even though the Plan stays within the 7-task ceiling.
- The pending PS-2420 CodeRabbit cleanup is outside this Scope and will not be folded in unless PS-2322 necessarily rewrites the exact same lines.

### Human-Approval Decision Points

1. **Canonical summary versus history:** Approve immutable full snapshots in append-only Linear comments, a replaceable versioned summary plus append-only events in the local run file, and tracker-first best-effort mirroring in hybrid mode.
   **Recommendation:** Approve, because it gives every mode the same logical contract without pretending Linear supports transactional comment replacement.
2. **Stale-state policy:** Decide whether any stale condition may be repaired in place.
   **Recommendation:** Permit repair only for an unambiguous non-authoritative reference that live systems prove exactly, show the proposed correction, and require explicit human confirmation; changed Scope, invalidated Plan, stale approval, missing branch, or changed delivery range must restart from the last still-valid human-owned boundary.
3. **Dirty worktree policy:** Decide when a partially modified worktree may resume.
   **Recommendation:** Offer continuation only when the current branch, recorded base and head, and full dirty diff are consistent with the recorded active bundle and the human confirms ownership; otherwise offer inspect and repair, restart without deleting changes, or cancel.
4. **Learning-candidate threshold:** Decide how aggressively Deliver and Evaluate should propose lessons.
   **Recommendation:** Require a specific observed fact, retained evidence, and a concrete implication for future work; default to no candidate for ordinary successful completion and generic test or review outcomes.
5. **File-count tripwire:** Approve or reject a one-bundle exception to the configured 12-file ceiling.
   **Recommendation:** Approve the exception because the overage is dominated by deterministic host and release projections, while the six tasks share canonical skills, state vocabulary, fixtures, and dependency arrows and therefore do not qualify for separate bundles.

### Tasks

#### Task 1: Specify the continuity state contract and behavioral oracle

- **Mode:** ai-delivered
- **Depends on:** none
- **Effort:** moderate (2-4 agent hours)
- **Execution posture:** test-first - write the behavioral corpus and expected decisions before changing the orchestration contract.
- **Description:** Define `spade-run-state/v1` as the logical current-state summary for one Scope and enumerate its required fields: Scope identity and revision, autonomy level, current phase, completed checkpoints, current bundle or task, repository and branch references, base and head commits where applicable, PR reference and state, last verification evidence with freshness, halt reason, next allowed action, state timestamp, and prior snapshot linkage.
  Define the corresponding event-history relationship and add fixtures for every interruption boundary, post-tripwire continuation, completed work, stale or contradictory state, dirty worktrees, learning and no-learning outcomes, duplicate candidates, and public or private routing.
- **Approach:** Single-source the schema, invariants, and mode mapping in `docs/FRAMEWORK.md`, with detailed triggered procedure in a canonical `src/skills/spade/references/` document and only a concise routing requirement in the always-loaded `/spade` skill.
  Add a dedicated blind continuity corpus and procedure under `tests/` so a fresh decider receives the live inputs without the expected result and must select resume, repair, restart, cancel, completed, or learning-capture behavior.
  Specify deterministic selection rules for the newest complete snapshot, explicit schema-version refusal, bounded evidence size, timestamp semantics, and redaction of secrets or sensitive authentication state.
- **Tracer-bullet outcome:**
  - **End-to-end behavior made usable:** A reviewer can take any versioned fixture snapshot and determine the exact live checks and permitted next decision without reconstructing the whole conversation.
  - **Highest practical test seam:** Fresh-context blind execution of the continuity corpus against the documented `spade-run-state/v1` contract.
  - **Blocking relationships:** No prerequisite; blocks Tasks 2, 3, 4, and 5; no external blocker beyond Plan approval.
- **Slice rationale:** This is an intentionally horizontal shared protocol and test oracle because persistence, resume, status, recovery, and learning capture must use one vocabulary before any vertical behavior can be implemented.
  Completion is observable when every Scope acceptance scenario has one expected corpus outcome and the schema has one canonical definition that later tasks consume.
- **Tests:** Validate that every required summary field and every acceptance fixture appears exactly once in the corpus, run the blind procedure against discriminating valid-versus-stale and learning-versus-no-learning pairs, and fail fixtures containing unknown schema versions, duplicate current summaries, or missing identity and next-action fields.

#### Task 2: Persist and report resumable state in every operating mode

- **Mode:** ai-delivered
- **Depends on:** Task 1
- **Effort:** moderate (2-4 agent hours)
- **Execution posture:** test-first - use the mode-equivalence and interruption fixtures to drive checkpoint writes and status reads.
- **Description:** Make `/spade` write a complete versioned summary at every existing stage boundary and meaningful delivery checkpoint, while retaining the current timestamped event trace and auto-decision log.
  Teach `/spade-status` to locate the current summary, display whether a run is resumable, halted, completed, or awaiting validation, and show only the recorded next action until live validation succeeds.
- **Approach:** In `linear` mode, append one clearly marked complete snapshot comment per checkpoint and use authoritative tracker ordering to identify the newest well-formed version.
  In `local` mode, store one run file under a stable Scope identity in `.spade/runs/`, replace only its delimited current-summary block, append only new event records, and refuse malformed or duplicate markers.
  In `hybrid` mode, write the tracker first and mirror the same logical state locally best-effort without elevating the mirror to authority.
  Keep state writes in skill prose and existing host primitives rather than adding an enforcement helper or background process.
- **Tracer-bullet outcome:**
  - **End-to-end behavior made usable:** After interruption at any stage boundary, `/spade-status` finds one current versioned snapshot and tells the human which live validation must happen before the run can continue.
  - **Highest practical test seam:** Mode-matrix behavioral fixtures that execute checkpoint write and status-read decisions for Linear, local, and hybrid state shapes.
  - **Blocking relationships:** Depends on Task 1; blocks Tasks 3, 4, and 5; hybrid mirror failures remain a non-blocking warning after a successful tracker write.
- **Tests:** Cover interruption after every `*:start` and `*:done` boundary, a tripwire halt, local repeat writes with no duplicate summary region, Linear snapshot ordering, hybrid tracker success with mirror failure, and status output for resumable, halted, completed, malformed, and unvalidated states.

#### Task 3: Validate live reality and continue from the next safe boundary

- **Mode:** ai-delivered
- **Depends on:** Task 2
- **Effort:** moderate (2-4 agent hours)
- **Execution posture:** test-first - make valid-resume, post-tripwire, changed-head, and already-completed fixtures fail before expanding `/spade` resume behavior.
- **Description:** On `/spade` invocation, detect an incomplete trace for the same Scope, reconstruct the run from live systems, and offer continuation only from the highest checkpoint whose prerequisites remain true.
  Treat already-completed stages as idempotent no-ops and never rerun Scope, review, Plan, approval, delivery, review, or PR operations that live evidence proves complete and current.
- **Approach:** Validate the tracker status, exact Scope identity and revision, Plan artefact and revision, task set, approval record and attribution, halt resolution, installed capability version, repository identity and base, branch existence and commit range, worktree state, current bundle or task, PR identity and state, required checks, and freshness of the last recorded verification.
  Use project-native Git and hosted-PR reads for repository and PR truth, and preserve the existing rule that branch names, trace text, and cached URLs are references rather than evidence.
  Present a bounded `Continue from <boundary>` decision only after all required checks pass, write the decision into the new snapshot, and preserve the chosen autonomy level and remaining tripwires.
  If the trace proves the selected autonomy level has already reached its halt point, report completion and the next human-owned gate without replaying work.
- **Tracer-bullet outcome:**
  - **End-to-end behavior made usable:** A human can invoke `/spade` after an interruption, see live evidence for the proposed boundary, choose continue, and proceed without repeating any completed valid stage.
  - **Highest practical test seam:** Fresh-context end-to-end behavioral runs over seeded tracker, Git, worktree, branch, PR, approval, and verification states.
  - **Blocking relationships:** Depends on Task 2; blocks Task 4 and final release; a human continuation choice is required before resumed mutation begins.
- **Tests:** Cover resume after each phase boundary, resume after a resolved tripwire, open-PR and merged-PR states, changed PR head invalidating prior review, already-completed work, Plan-level halt, Deliver-level halt, capability-version mismatch, and equivalent decisions in Linear, local, and hybrid modes.

#### Task 4: Fail closed and provide bounded recovery for stale or dirty state

- **Mode:** ai-delivered
- **Depends on:** Task 3
- **Effort:** moderate (2-4 agent hours)
- **Execution posture:** test-first - drive the refusal and recovery matrix from missing, contradictory, stale, and dirty-state fixtures.
- **Description:** Classify failed resume validation into explicit stale, contradictory, missing, unsupported-version, and dirty-worktree outcomes, then offer only inspect and repair, restart from a named valid boundary, or cancel.
  Prevent continuation past a changed Scope, invalidated Plan, stale or absent approval, missing branch, unresolvable PR, changed delivery range, stale verification, or unexplained worktree modifications.
- **Approach:** Permit repair only when authoritative live state proves one exact correction to non-authoritative recorded metadata, preview the replacement, and require human confirmation before writing a superseding snapshot.
  Require a Scope or Plan restart when human-owned intent, criteria, Plan, or approval has changed.
  For a dirty worktree, compare the complete diff with the recorded branch, base, head, active bundle, and task, preserve every user change, and never auto-stash, reset, delete, switch branches, or claim ownership.
  Record every refusal and human decision durably so a later invocation does not repeat or bypass it.
- **Tracer-bullet outcome:**
  - **End-to-end behavior made usable:** An invalid resume attempt stops with the exact contradiction and presents only recovery actions that preserve user work and human-owned gates.
  - **Highest practical test seam:** End-to-end recovery-decision fixtures with seeded changed Scope, stale approval, missing branch, invalid Plan, changed PR range, malformed snapshot, and matching or unrelated dirty diffs.
  - **Blocking relationships:** Depends on Task 3; blocks final release; repair and restart paths require an explicit human choice, while cancel has no blocker.
- **Tests:** Prove that every stale or contradictory case refuses continue, that only an exact evidence-backed metadata correction can offer repair, that restart names the last valid boundary, that cancel writes no mutation beyond its audit event, and that dirty changes survive every path byte-for-byte.

#### Task 5: Surface deduplicated learning candidates through `/spade-learn`

- **Mode:** ai-delivered
- **Depends on:** Tasks 1 and 2
- **Effort:** moderate (2-4 agent hours)
- **Execution posture:** characterization-first on the existing `/spade-learn` capture and refresh gates; test-first on automatic candidate detection and deduplication.
- **Description:** At delivery verification boundaries and after Evaluate synthesizes its review axes and evidence matrix, identify only specific candidate lessons caused by a failed assumption, recurring pitfall, newly discovered project constraint, reusable pattern, or correction to an active learning.
  Reuse `/spade-learn` to present one evidence-backed deduplicated draft and require the human to choose public-safe, private, or skip before any file is written.
- **Approach:** Characterize the existing capture, public-private routing, and refresh behavior before adding a candidate entry path.
  Build candidates only from named delivery facts, review findings, failed or corrected checks, evaluation gaps, and explicit human corrections, never from unrestricted transcript mining or generic task completion.
  Require each candidate to state the observation, evidence source, future planning implication, originating Scope, and proposed tags.
  Compare the draft with active public and private project learnings before display, recommend update or supersession through the existing human-gated refresh rules when a match exists, and otherwise pass the draft into the existing public-safe, private, or skip decision.
  Before the choice, persist at most a content-free pending-decision checkpoint needed for resumability and never persist the draft, body, or proposed tags.
  After the choice, record only `candidate:none`, `candidate:skipped`, `candidate:captured-public`, `candidate:captured-private`, or the approved duplicate-resolution outcome in the run state.
- **Tracer-bullet outcome:**
  - **End-to-end behavior made usable:** A real failed assumption or reusable constraint produces one deduplicated draft that the human can route to public, private, or skip, while an ordinary successful task produces no prompt and no file.
  - **Highest practical test seam:** Behavioral invocation of Deliver and Evaluate candidate hooks through the existing `/spade-learn` decision and filesystem boundary.
  - **Blocking relationships:** Depends on Tasks 1 and 2; blocks Task 6; every write is blocked on the human's public-safe, private, or skip choice, and duplicate replacement is additionally blocked on the existing refresh approval.
- **Tests:** Cover all five candidate categories, generic no-learning completion, duplicate active public and private entries, a correction that archives only after approval, public routing, private routing, skip, sensitive-detail redaction, no silent write, and unchanged Plan-time matching of active Markdown learnings.

### Delivery Sequence

1. Task 1 establishes the shared contract and failing behavioral oracle.
2. Task 2 makes checkpoint persistence and status reporting mode-equivalent.
3. Task 3 implements valid live-state reconstruction and safe continuation.
4. Task 4 adds fail-closed recovery and dirty-worktree conservation after the valid path is stable.
5. Task 5 integrates evidence-backed learning candidates with the established human-gated store.
6. Task 6 regenerates, versions, and validates the complete release surface.

The tasks are deliberately sequential because Tasks 2-5 share the state vocabulary and canonical `/spade` surface, while Task 6 must observe the final combined behavior.
