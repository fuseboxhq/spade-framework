# Plan: Tighten review and merge using lessons from EGM and Anthropic's code review post (6.1.0)

Scope: https://linear.app/m-kopa/issue/PS-3214
Approved by Kevin Robertson, 2026-11-01, with tripwires 5 and 6 acknowledged; the human merges.

## Acceptance criteria (snapshot)
1. On-green merge denied for secrets, production data, permission widening, CI, destructive migrations, or `guards.human_merge_paths`; ordinary PRs and additive migrations still merge.
2. Unreadable changed files (or migration patch) deny the merge.
3. Every blocking finding ends fixed, contested with evidence, escalated, or pre-existing; escalated or evidence-free contests block an agent-recorded PASS.
4. A reviewer that did not run (after one retry) is "not run" and blocks an agent-recorded PASS.
5. Findings in code the diff did not change are pre-existing, do not block PASS, and become Leads.
6. Delivery Review capped at three rounds, middle rounds diff-aware, settled findings not reopened, PASS round covers full base..head, fourth round with a blocker halts.
7. Deliver PR body has Risk and How to revert; after Evaluate it carries the Evaluate table and dispositions; on-green squash uses that body.
8. Plan template snapshots the Scope's acceptance criteria.
9. `setup` can register the guard hooks idempotently without clobbering other settings.
10. Released as 6.1.0; `./scripts/lint/run-all.sh` passes.

## Approach
Extend `guard_merge` to list the PR's changed files through `gh api --paginate repos/{owner}/{repo}/pulls/<n>/files`, which returns each file's `filename`, `previous_filename` for renames, `status`, and `patch`.
Both the new and the old name of every file are classified, and the merge is denied when the listed count differs from `changedFiles` on `gh pr view` (GitHub caps the files API at 3000), when a file is protected, or when it matches `guards.human_merge_paths` (comma-separated globs).
Protected at merge means secrets, production data, or permission widening (the existing deliver-mode classifier), or CI (its own small case).
Migrations get their own check, not the existing classifier, which files `*.sql` under schemas: a path with a `migrat` word or under `db/migrate` is a migration, and it denies when its patch is missing or its added lines contain `drop`, `rename`, `truncate`, `delete`, `remove_`, `Remove`, `alter column`, `change_column`, or `AlterField`.
The CI check is lifted into its own small case so the merge floor does not pull in the full 14-category list, which would stop on-green working (release matches `package.json`, governance matches `src/` here).
Review and Evaluate changes are skill and FRAMEWORK text: one disposition taxonomy, a "not run" rule, a pre-existing tag in the reviewer contract, and a three-round cap folded into tripwire 2.
The durable record goes in the PR body (`gh pr edit` does not move the head), and the on-green merge passes it with `--body-file`.
`setup --hooks` opts a clone install into the guard hooks by merging the entries from `src/hooks/hooks.json` into `~/.claude/settings.json` with jq, rewriting each command to the clone's absolute `bin/spade-guard` (`${CLAUDE_PLUGIN_ROOT}` is only set for plugin hooks).

Rejected forks:
- All 14 categories at merge: rejected, on-green would effectively never fire in this repo or any repo with a `package.json`.
- Registering hooks by default in `setup`: rejected, it edits a user's global settings unasked; without hooks guards are inert and SPADE already fails closed to a human merge, so opt-in loses nothing on safety.
- Record in a commit after review: rejected, it breaks the SHA pin. A PR comment: rejected, it does not reach git history.
- Pre-existing detection by git blame inside the reviewer: rejected, the reviewer has Read/Grep/Glob only; the coordinator confirms with `git show <base>:<path>`.

## Risks
- Skill byte budgets in `lint-skill-authoring.sh` may be tight; the text has to stay short.
- Destructive-migration detection is a keyword match on added lines covering SQL, Rails, and Django verbs; a false negative is possible for other ORMs, a false positive only costs a human merge.
- The skill text must name the PR number first in the merge command, because the guard reads the first non-flag token as the PR.
- Release mechanics (projections, lifecycle fixture, seal) are fiddly; the post-merge seal is a known follow-up (PS-3028).
- No guards are live in the delivering session, so the whole change touches protected surfaces (tripwire 6) and the human merges.

## Review

The Approach and tasks above now address each one; none changes the approach.
