# Plan: The SPADE guard follows the repository each tool call targets

Scope: https://linear.app/m-kopa/issue/PS-3305
Approved by Tiago Pascoal, 2026-11-19 (revision 3, including the reworded AC 1–3 and 6 and edits to the protected guard and `FRAMEWORK.md`).

Learnings read: `2026-09-08-guards-need-a-tokenizer-not-a-regex` (PS-3017, PS-3026). It applies directly in two ways:
- `cd` targets and the operator between segments come from the guard's tokenizer, never from the raw string.
- Every new rule gets a fixture in both directions: the evasion must be denied, and the everyday form must still be allowed.

Revision 2, 2026-11-19, after the Scope and Plan review (general and security lenses). Revision 1 resolved every call to "the nearest `.spade/config` above the path". The reviewers showed that an agent can steer that rule, and that it breaks single-repository sessions:
- An agent could write a permissive config in any subfolder, or `cd` somewhere with no config at all.
- The framework repository itself has 37 nested fixture configs.

Revision 2 records the session's repositories when the session starts and only resolves to those. This changes the wording of AC 1–3, so the amended criteria below need your approval along with the Plan.

Revision 3, 2026-11-19, after a re-review of revision 2:

- **The list is recorded once per session.** SessionStart also fires on compact, resume and clear, so the list is written only if it doesn't exist yet.
- **Edits are never judged more loosely than today.** "Outside the armed repository" is now lexical. A file inside the armed repository is classified relative to the armed repository and relative to its own session repository, and is denied if either matches.
- **Skills and the guard read the same list.** Skills decide live and marker locations from the recorded list instead of `git rev-parse` or "at or above".
- **No `git` at SessionStart.** A git top level is a folder containing `.git`, as a directory or a file. That avoids symlink and `safe.directory` mismatches, and drops the extra tool.
- **The tokenizer marks subshells and substitutions.** Any `(`, `)`, backtick or lifted substitution before a merge makes the directory unknown.

## Acceptance criteria

Revision 2 rewords AC 1–3 to "the repository recorded for the session" in place of "the nearest `.spade/config`". AC 4–8 are as scoped, plus the review's checks on message text and on where `gh` runs.

1. **Edits use the file's own repository.** An Edit, Write, MultiEdit or NotebookEdit call is judged by the session repository that contains the target file. When several contain it, the deepest one wins. That repository decides the protected-path check, the framework-repo detection and the `mode` marker. A `.spade/config` that an agent creates in a subfolder never becomes a repository. `tests/hooks/guards.sh` cases cover:
   - an edit in a child repository from a session opened in its parent
   - the planted-config evasions from the review, which must still be denied
2. **Commands use their working directory's repository.** A Bash call is judged by the session repository that contains its working directory. That directory is the hook input's `cwd`, changed by `cd <literal path>` segments joined with `&&`, or by `git -C <literal path>` for the stage-all check. The merge policy, the reviewed-head record and every `gh` call come from that repository. A `guards.sh` case runs `cd <child> && gh pr merge N --match-head-commit <sha>` from a parent session that has no merge policy:
   - The merge is judged under the child's `on-green` rules: allowed when every condition holds, otherwise denied with the condition that failed.
   - The `gh` stub proves it ran in the child.
3. **Parent folders without a config still get guards.** A session opened in a folder with no `.spade/config` still gets guards in any child git repository that has one, one or two levels down. A `guards.sh` case covers it. A folder with none nearby gets nothing written.
4. **Cross-repository merges stay closed.**
   - `-R`, `--repo`, `GH_REPO` and a PR URL are still denied under `on-green`.
   - A merge is denied, and the message says why, when the working directory is one of these:
     - unknown: a variable, a substitution, or a directory-changing form the guard doesn't model
     - outside every session repository, when the session folder has no config of its own
   - `guards.sh` cases check that reason text, and cover both directions from PS-3283.
5. **Deny messages name their config.** Every deny that depends on config says which `.spade/config` it read. `guards.sh` checks the text (PS-3283).
6. **Skills can tell from a child repository that guards are live.** Guards are live for a repository only when the session's recorded list (`.spade/guard/<session>/repos`, found at or above it) names that repository. A repository created mid-session is therefore not live and stays on the strict model. `docs/FRAMEWORK.md` documents the check in § Mechanical guards and § The Deliver level step 3. `/spade-evaluate` and `/spade-quick` use it, and `/spade-evaluate` writes `reviewed-head` in the listed repository the guard will read. `guards.sh` cases cover a listed child, an unlisted mid-session worktree, and a session folder below its git top level.
7. **Single-repository sessions behave exactly as today.** Every existing case in `tests/hooks/guards.sh` passes without changing what it expects. New cases pin the specific single-repository regressions the review raised:
   - a nested fixture config
   - `cd /tmp && gh pr merge --repo …`
   - `git --git-dir … add -A`
   - an edit outside the repository while armed
8. **Copies and docs stay in step.** `docs/FRAMEWORK.md` and its reference copies describe the new behaviour. The three guard copies (`bin/`, `scripts/`, `plugins/spade-framework/scripts/`) stay byte-identical, and the repository's checks and CI pass.

## Approach

**Session repositories, recorded once at the session's first SessionStart.** The first SessionStart runs before the agent can act, so it decides which repositories count, and writes the list to `.spade/guard/<session>/repos`. Later SessionStart events (compact, resume, clear) find the list already there and leave it alone, so a repository created mid-session never joins it. A `guards.sh` case sends a compact event after a planted `git init`. A session repository is one of these:
- The session folder (`CLAUDE_PROJECT_DIR`, else `$PWD`), if it has a `.spade/config`. This is exactly today's single project.
- Any child or grandchild folder that contains `.git` (a directory, or the file a worktree has) and a `.spade/config`. The guard finds these with the shell globs `"$root"/*/.spade/config` and `"$root"/*/*/.spade/config`, so there's no `find` and no `git` call. Hidden folders such as `~/.spade` don't match `*`. Folders without `.git`, such as test fixtures, are skipped.

Where it writes:
- If the session folder has a config, `live` and `repos` go in its `.spade/guard/<session>/`, as today.
- If it doesn't, both go in each recorded child's `.spade/guard/<session>/`. Nothing is written into the session folder itself, so a session opened at `~` never touches `~/.spade`.
- If no repository is found at all, nothing is written and the guard stays inert. That's today's behaviour for non-SPADE folders, and it still exits before needing `jq`.
- **How PreToolUse finds the list.**
  - **Session folder has a config.** The guard reads the list there. If `jq` is missing it exits 2, as today.
  - **Session folder has no config.** The guard first checks the same globs. If nothing matches, it exits before `jq`. If `jq` is missing, it stays inert: today such a session has no guards at all, and skills will see "not live" and stay strict. Otherwise it reads every existing `.spade/guard/<session>/repos` copy in the matching children. A matching child with no copy, such as a worktree added mid-session, is ignored. If two copies disagree, the guard treats them as tampered: merges and armed edits are denied with that reason.

**Resolution.** `repo_for <abs-path>` returns the deepest recorded repository containing the path. Paths are lexically normalised as today, and symlinks aren't followed, which matches the current `relative_path`. When no recorded repository contains the path:
- **Session folder has a config:** fall back to the session folder. That's today's behaviour, so `cd /tmp && gh pr merge --repo X` is still judged by the session's config.
- **Session folder has no config:**
  - A merge is denied as outside the session's repositories.
  - An edit is denied if any session repository is armed, and allowed otherwise.
  - Stage-all is inert.

Configs an agent writes later never join the list, so planted configs and fresh clones don't count.

**Working directory for Bash.** The directory carries across lines. A newline ends a segment the way `;` does, so `cd child` on one line followed by a merge on the next makes the directory unknown. The tokenizer gains a leading field on each segment. It's leading, so `guard_merge` still parses the PR number from the same position. It records the character that ended the segment (`&`, `|`, `;`, `(`, `)`, backtick, end) and whether the segment was lifted out of a substitution. A `&&` shows up as two `&` ends around an empty segment, and the walker reads it that way. Any `(`, `)`, backtick or lifted segment before the checked segment makes the directory unknown, so `cd /a && (cd /b && true) && gh pr merge …` is unknown. The effective directory works like this:
- It starts at the hook `cwd`.
- `cd [--|-L|-P] <dir>`, joined to the next segment by `&&`, moves it. `~` and `~/…` expand to `$HOME`, and relative paths resolve against the current value.
- It becomes **unknown** in any of these cases:
  - a `cd` joined by anything other than `&&`
  - a `cd` argument with `$` or a substitution placeholder
  - `cd -`, `pushd`, `popd`, `builtin cd` or `command cd`
  - `env -C`
  - a segment with a `CDPATH=` prefix
  - a subshell
- An unknown directory denies a merge. For stage-all, `git -C <literal>` sets that segment's directory, and `--git-dir`, `--work-tree`, `GIT_DIR` or `GIT_WORK_TREE` make it unknown. An unknown directory is judged against the session folder's config when it has one, as today. Otherwise it's denied if any session repository sets `deny_stage_all`.

**Markers per repository.**
- `mode` counts only at a session repository's own `.spade/guard/<session>/mode`. A decoy `mode` file in a subfolder is ignored.
- **The armed repository** is the session repository whose `mode` is set.
- **An edit outside the armed repository is denied.** "Outside" means lexically outside its folder, exactly today's "outside the project root" rule, now also across siblings.
- **An edit inside the armed repository** is classified twice: relative to the armed repository, which is today's classification, and relative to its own session repository when that's a different, deeper one. It's denied if either matches. So an armed `~/argus` editing `~/argus/argus-web/.claude/settings.json` is denied, as today. A child armed in deliver mode gets the child's root-anchored categories. No edit is judged more loosely than today. `guards.sh` covers an armed parent editing a child.
- `reviewed-head-<pr>` is read from the target repository's `.spade/guard/`.

**Skills.** One rule shared with the guard: the **session repository for a folder** is the deepest repository in the recorded list that contains it.
- **Live** is decided like this: find the nearest folder at or above this one that contains `.git` or `.spade/config`. Guards are live only if that folder is itself in the recorded list.
  - A worktree or clone added mid-session has its own `.git`. It isn't listed, so it isn't live, even when it sits inside a listed repository such as `~/argus` or a repository's `.claude/worktrees/x`.
  - The guard still judges its edits as part of the outer repository, as today.
  - `guards.sh` covers a worktree nested inside a listed parent that has a config, and an in-repo `.claude/worktrees/x`.
- `/spade-evaluate` writes `reviewed-head-<pr>` in the session repository for the PR's working folder. In a single-repository session that's the project folder, as today, even when it sits below its git top level.
- `/spade-quick` and `/spade` arm `mode` in the session repository they deliver in.
- If the folder isn't in the list, for example a worktree added mid-session, guards aren't live there and the skill stays strict.
- `docs/FRAMEWORK.md` § Mechanical guards states the rule, and § The Deliver level step 3 and the skills link to it.

**Messages and tests.**
- Config-dependent denies end with `(read <path>/.spade/config)`.
- New cases use an `expect_deny_reason` helper and a `gh` stub that records `$PWD`. Existing cases keep their helpers and expectations unchanged.

**Shipping.**
- `bin/spade-guard` is canonical. `scripts/project-hosts.sh` regenerates the copies.
- The CHANGELOG gets an entry, with no version bump (no fragment change, like #15).

**Rejected forks**
- *Nearest `.spade/config` above the path* (revision 1). An agent could steer it with a planted config, and it changed single-repository sessions that contain nested fixture configs.
- *Accept only a config that is tracked and unmodified in git.* That stops planted files, but not a fresh clone or a commit in a scratch clone. The SessionStart record is simpler, and closes both within a session. A repository planted in one session is listed from the next, which is the marker-forgery class in Risks.
- *A per-user state folder for markers.* ARCHITECTURE.md says SPADE keeps no state outside `.spade/`.
- *Resolve and allow `-R owner/repo`.* That widens the merge surface, and the Scope keeps cross-repository merges closed.
- *A `spade-guard --status` subcommand.* The "at or above" check answers the same question in one line.

## Risks

- **Scope wording changes.** AC 1–3 and AC 6 now say "session repository" instead of "nearest config". That's your call, as part of this approval. The toolset stays as scoped.
- **Repositories created mid-session aren't covered.** A worktree or clone added after the session starts isn't in the list. Guards aren't live there, and skills stay strict, until the next session. That's deliberate, and the docs will say it. You add worktrees under `~/argus` often, so expect strict mode in those until you restart.
- **Marker forgery is still possible.** An agent could still write `repos`, `mode` or `reviewed-head` with ordinary shell commands, and Bash can already edit a real `.spade/config`. That's PS-3025's territory, and today an agent can already forge `reviewed-head`. `repos` is one more forgeable file. The Delivery Review showed that, as first built, the Write tool could steer a merge through it without Bash, by writing an unlisted child's `.spade/config` and adding the child to `repos`, so an armed session now treats `repos` as permission widening. With Bash it stays forgeable, as `mode` and `reviewed-head` are. Two forgeries go away: decoy `mode` files and planted configs. Re-running SessionStart can't add to the list.
- **The hook `cwd` may not follow the shell.** I'll confirm once in a live session and record the result in the PR. If the hook only ever reports the session folder, the `cd … &&` form still works, and a bare merge from a child directory denies (parent without a config) or uses today's config (parent with one).
- **Tokenizer change.** The new leading segment field touches the code the learning warns about. The existing consumers skip it, and the existing cases protect them. Task 2 adds newline fixtures in both directions.
- **Already true before this change:** deliver mode doesn't protect a `.spade/config` below the root, because only the root one is anchored at `bin/spade-guard:186`. This Plan narrows that only for listed child repositories. Adding `*/.spade/config` to the permission-widening category belongs in its own Lead.
- **Size.** About 8 canonical files: the guard, tests, `FRAMEWORK.md`, three skills, the CHANGELOG, and maybe `PATTERNS.md`. That's under the 12-file ceiling. The regenerated projections add about 50 more, as #15 did.
- **Upstream review.** The PR comes from your fork, and the `fuseboxhq/spade-framework` maintainers decide the merge.
- **No conflict** with ARCHITECTURE.md, PATTERNS.md or ANTI-PATTERNS.md. The checks stay deterministic over tool input and named local state, with no workflow logic.
