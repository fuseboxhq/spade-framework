## Human Approval Decision Points

### Decision 1: Canonical protected-surface taxonomy

**Recommendation:** Approve one canonical `Security-sensitive path surface` section in `docs/FRAMEWORK.md`, referenced by Deliver tripwire #6 and `/spade-unhinged`, with the following protected categories and a fail-closed default.

1. **Authentication and identity:** auth, authentication, authorisation, session, identity, and login boundaries.
2. **Secrets and credentials:** secrets, credentials, tokens, environment-secret material, private keys, certificates, and key stores.
3. **Cryptography:** encryption, decryption, signing, verification, hashing used as a security control, and key management.
4. **Permissions and IAM:** access control, roles, policies, RBAC, permission grants, `.claude/settings.local.json`, and any permission widening.
5. **Schemas:** application, database, event, API, and infrastructure schemas whose change affects persisted or trusted structure.
6. **Migrations and backfills:** schema migrations, data migrations, backfills, and lifecycle migration definitions.
7. **Production data:** paths or commands that read, write, transform, export, delete, or repair production data.
8. **CI:** workflow definitions, CI scripts, runner permissions, and CI credential or execution configuration.
9. **Release:** version authority, release manifests, changelogs used by release tooling, release provenance, and publication configuration.
10. **Deploy:** deployment scripts, deployment configuration, rollout controls, and production environment definitions.
11. **Infrastructure:** infrastructure-as-code, cloud resource definitions, network and platform policy, and privileged operational configuration.
12. **Kubernetes:** manifests, operators, admission policy, RBAC, namespaces, and cluster configuration.
13. **Helm:** charts, templates, values that affect deployed resources, and release hooks.
14. **Framework governance, execution, and fetch surfaces:** consumer framework-marker regions; `docs/FRAMEWORK.md`; root governing files including `AGENTS.md`, `PATTERNS.md`, `ANTI-PATTERNS.md`, and `INTENT.md`; canonical and generated skill contracts; `src/CAPABILITIES.md`; `setup`; `setup.ps1`; `bin/**`; lifecycle and release manifests; anything changing what `spade-update-check` fetches; and the `.spade/config` `handoff` block plus `.spade/handoff.local`.

## Architectural Alignment and Conflicts

- **One explicit process conflict requires approval.**
  Current governing rules forbid repository mutation outside a Scope or valid quick-path gate.
  `/spade-unhinged` intentionally introduces a third, non-shipping experimental exception, so Decision 2 must be approved as a real invariant amendment rather than hidden in skill prose.
- **The Deliver security definition is a live safety contract.**
  Moving its inline list without characterization could narrow unattended halt behavior.
  Task 1 therefore captures every existing category first, records a blind baseline, and accepts the extraction only if all legacy cases still halt while clean controls still proceed.
- **No runtime or dependency is introduced.**
  Behavior remains prose-first and uses bounded Git reads through `{{SPADE_SHELL}}`; no daemon, package manager, executable classifier, or external state store is added.
- **Canonical source remains under `src/`.**
  Generated host, plugin, marketplace, and global-install payloads are updated only through `scripts/project-hosts.sh`.
- **`/spade` does not gain a fifth autonomy option.**
  Its picker remains Deliver, Plan, Scope, Stub.
  The only orchestrator edit is the reference from tripwire #6 to the canonical protected-surface definition.
- **The new skill is orthogonal rather than casual command sprawl.**
  `/spade-quick` owns land-intended trivial work, the full loop owns non-trivial delivery, and `/spade-frontier` owns consequential fog.
  `/spade-unhinged` owns only an explicitly confirmed, throwaway experiment that is not approved to land.
- **`src/skills/spade-review/SKILL.md` remains untouched.**
  Neither command routing nor the protected-surface contract belongs there.
  If delivery appears to require editing it, stop and return to Plan review rather than consuming its approximately 105-byte budget headroom.
- **No other architecture conflict was found.**
  The proposed behavior fits the existing Markdown, progressive-disclosure, host-adapter, idempotent-fragment, immutable-provenance, and human-owned Ship boundaries.

## Risks and Assumptions

- **R1 - Safety-set narrowing during extraction:** A prose move could accidentally omit a current Deliver halt.
  Mitigation: characterize the current inline list before editing it, retain legacy cases as permanent controls, and require clean and protected discriminating pairs before and after extraction.
- **R2 - Category ambiguity:** Repository-specific paths may not contain obvious keywords.
  Mitigation: classify by path and declared purpose against the canonical taxonomy, show the evaluated inventory, and treat every unclassifiable path as protected.
- **R3 - Mid-run path expansion:** A safe experiment may later touch a protected file.
  Mitigation: rerun the full tracked and untracked path gate before each new path and stop before mutation when the candidate path is protected or unknown.
- **R4 - Dirty-worktree ownership:** Existing safe changes may be overwritten or mistakenly attributed to the experiment.
  Mitigation: use read-only preflight, show complete tracked and untracked state, require Continue or Cancel, preserve every byte, and never stash, reset, clean, overwrite, switch away from owned work, or guess ownership.
- **R5 - Primary-branch experimentation:** Continuing on a primary branch could make later retention unsafe.
  Mitigation: require an explicit Continue or Cancel decision before mutation and require a dedicated `spade-unhinged/<slug>` branch before any commit or draft PR.
- **R6 - Audit laundering:** A draft experiment PR could be mistaken for reviewed delivery.
  Mitigation: fixed `[unhinged]` title prefix, Draft state, structured body, visible `not approved for merge` statement, merge refusal, and mandatory closure plus normal SPADE rerouting before preservation.
- **R7 - Destructive action leakage:** The word unhinged could be interpreted as permission to bypass ordinary safety checks.
  Mitigation: the entry briefing states that destructive confirmations, sandbox boundaries, permission limits, and no-overwrite rules remain fully active, and that Continue never authorises permission widening, sandbox bypass, or skipping a destructive confirmation.
- **R8 - Artifact creep:** The experiment path could silently create Linear issues, run state, learnings, or approval records.
  Mitigation: blind negative controls assert that entry and exit create none of those artefacts, and the only durable experiment audit is the optional draft PR when work is retained or shared.
- **R9 - Skill budget growth:** A complete safety contract could exceed the 32,768-byte always-loaded limit.
  Mitigation: keep routing, invariant, gate, and completion rules in `SKILL.md`; route only the branch-specific draft-PR procedure to one canonical reference; fail lint rather than increasing the budget.
- **R10 - Release fixture circularity:** The v3.3.0 fixture must cite an immutable commit containing the released fragments.
  Mitigation: create one release-content commit after canonical and projected behavior is complete, then generate and commit the provenance fixture from that exact commit in Task 6.
- **R11 - Generated-file volume:** Projection and release ripple will dominate the diff and trigger the configured file ceiling.
  Mitigation: require Decision 3, review canonical files first, and use projection drift plus install checks to verify generated material.
- **R12 - Canonical Scope reconciliation:** Linear is unavailable to this planning agent, so the orchestrator-provided Scope text is the planning authority for this file.
  Mitigation: the orchestrator should compare this Plan with the complete current PS-889 description before recording approval or creating sub-issues.
