# Plan for: Delivery assurance: tracer-bullet Plans, two-axis review, and acceptance evidence

**Scope:** PS-2319

**Delivery shape:** One bundle, six tasks, one pull request.

## Technical Approach Summary

Extend the existing Plan, Review, Deliver, and Evaluate prose contracts so every planned task names a usable vertical outcome, delivery is reviewed against one immutable base/head range on two independent axes, and Evaluate records criterion-level evidence before the human selects PASS, PARTIAL, or FAIL.
Keep the always-loaded skills concise by routing detailed delivery-review and evidence-matrix procedures into canonical `src/skills/**/references/` files, then regenerate every host projection from `src/`.
Use the repository's existing lint, behavioral-corpus, projection, and blind-context patterns rather than adding a runtime, bundled browser, or new review role.

## Human Approval Decision Points

### Decision 1: Evidence bar

**Recommendation:** Approve a risk-proportionate evidence bar that is strict about freshness and criterion coverage but conditional about evidence type.

- Every acceptance criterion must appear once in the evidence matrix and be classified as `diff-verifiable`, `runtime-verifiable`, `external-state`, or `human-only`.
- Diff-verifiable evidence must cite the fixed reviewed range and the relevant files or hunks.
- Runtime-verifiable evidence must be produced during the current evaluation against the recorded head SHA and must include the command, exit status, and concise result.
- UI evidence is required only for UI criteria and must use the project-native browser or QA tooling appropriate to the claim, with screenshot or rendered-state evidence and console or network evidence when those surfaces are material.
- External-state and human-only criteria remain explicitly open until authoritative evidence or human confirmation is supplied.
- PASS is available only when every criterion is satisfied with current evidence and no unresolved delivery-review finding makes the work unfit to ship.
- Small backend changes do not inherit UI ceremony when no criterion or changed behavior has a UI surface.

**Approval requested:** Accept this bar or identify any class that should be stricter or more permissive before Task 1 locks the behavioral oracle.

### Decision 2: Evaluate ownership boundary

**Recommendation:** Keep the agent responsible for gathering evidence, running project-native checks, performing the two independent review axes, and recommending a verdict, while the human remains the final owner of PASS, PARTIAL, or FAIL and of the Done and Ship decisions.

- Delivery-review findings are advisory inputs to Evaluate, not a new phase and not an autonomous shipping decision.
- The agent must not convert missing evidence, unverifiable external state, or human-only confirmation into a pass.
- The existing explicit post-Evaluate merge authorization remains unchanged.

**Approval requested:** Confirm that this assistance-versus-ownership line is the intended boundary.

## Architectural Alignment and Conflicts

- **No architectural conflict found.**
  The plan remains Markdown plus bounded shell lint, edits only canonical behavior under `src/`, uses fixed host adapters, and adds no service, dependency, browser runtime, or external integration.
- **The required tracer-bullet field is a breaking Plan contract.**
  PATTERNS.md requires a major version bump for breaking skill-contract changes, so the recommended release target is v3.0.0 with the corresponding capability, fragment, migration, changelog, documentation, and projection updates.
- **Existing approved and historical Plans remain readable.**
  The new field is mandatory for newly generated or revised Plans, while downstream readers identify a pre-v3 Plan as legacy rather than retroactively invalidating its audit trail.
- **The existing `/spade-review` advisory boundary remains intact.**
  Its new Delivery Review mode produces independent findings and a bounded synthesis; `/spade-evaluate` consumes those findings, and the human still owns the verdict.
- **Progressive disclosure is required.**
  `spade-review` is already a large skill under the authoring budget, so detailed fixed-range and axis procedures belong in a routed canonical reference rather than expanding the always-loaded body unnecessarily.

## Risks and Assumptions

- **R1 - Fixed-base portability:** Hosted PR, committed local branch, and tracker-backed workflows expose git state differently.
  Mitigation: record exact `base_sha` and `head_sha` plus their resolution source once per review, run both axes against that same immutable range, and refuse PASS if the head changes or a clean committed range cannot be established.
- **R2 - Review-axis bias:** A single context could let Scope findings suppress engineering-standard findings.
  Mitigation: dispatch the Scope/acceptance axis and repository-standards axis independently with the same diff range, then synthesize only after both complete.
- **R3 - Review volume:** Two axes can produce more findings than a human can use.
  Mitigation: reuse the existing severity and convergence concepts, show every blocking finding, bound inline major findings, collapse minors to a count, and preserve the full report.
- **R4 - Evidence ceremony:** A universal UI checklist would burden non-UI work without increasing confidence.
  Mitigation: choose evidence by criterion classification and risk, not by a fixed cross-project checklist.
- **R5 - Stale evidence:** Commands run before the final code or reviewer-applied changes can look current while testing an older head.
  Mitigation: bind runtime and UI evidence to the final reviewed head SHA and invalidate it whenever the head changes.
- **R6 - Legacy Plans:** Archived Plans lack tracer-bullet fields.
  Mitigation: keep legacy read compatibility and enforce the new field only when generating or revising a v3 Plan.
- **R7 - Autonomy size ceiling:** Canonical skill changes, release metadata, behavioral fixtures, and generated host projections will exceed the configured 12-file ceiling even though the Plan has only six tasks.
  Mitigation: halt for human review as required, then keep one semantic bundle because splitting generated projections or mutually dependent contracts would create inconsistent intermediate releases.
- **R8 - Governing-skill tripwire:** Phase 2 changes the orchestrator and evaluation rules that Deliver treats as security-sensitive governing surfaces.
  Mitigation: require the explicit human Plan approval before delivery and do not treat Deliver-level auto-approval as authority to rewrite these contracts unattended.
